# django-sms-uz 2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild `django-sms-uz` as a tested, pooled, backend-pluggable Django SMS app importable as `uzsms`, without renaming the database table or the PyPI distribution.

**Architecture:** A lazy settings proxy feeds a swappable backend interface; a thin client orchestrates validation, bulk logging, and one batched provider call. DRF, httpx, and Celery are optional extras behind guarded imports. Old public names survive as deprecation shims.

**Tech Stack:** Python 3.9–3.13, Django 4.2/5.x, requests, pytest + pytest-django, responses/respx, ruff. Optional: djangorestframework, httpx, celery.

**Spec:** `docs/superpowers/specs/2026-09-08-uzsms-2.0-refactor-design.md`

**Note on format:** This plan deliberately contains no code snippets, per the repository owner's global instructions. Tasks are specified by file path, interface signature, and expected behavior. Implementers write the code at execution time and must follow TDD: the test is written and observed failing before any implementation.

## Global Constraints

- Import package: `uzsms`. Django app label: **`SMS`** (pinned, never changed).
- Database table stays `SMS_smslog`. Migrations `0001`–`0003` keep their exact filenames.
- PyPI distribution name stays `django-sms-uz`. Settings key stays `SMS_SETTINGS`.
- Version becomes `2.0.0`.
- `requires-python >= 3.9`. Runtime deps: `django>=4.2`, `requests>=2.28`. Nothing else is a hard dependency.
- Importing `uzsms` with no `SMS_SETTINGS` defined must never raise.
- No public method may return a raw `requests.Response` or a bare string.
- Every outbound HTTP call passes an explicit `timeout`.
- `message_id` is generated once per `SmsMessage` and reused across retries.
- Commit messages end at the last line of the body. No attribution trailers.
- Every task ends with a passing `pytest` and `ruff check .`.

## Owner decisions taken mid-execution (supersede the task text below)

These were decided by the repository owner after the plan was written. Where a task section
below contradicts one of these, the decision wins.

- **D1 — One migration file, hard break.** The three legacy migrations and the planned `0004`
  are replaced by a SINGLE `0001_initial.py` carrying the final 2.0 schema. Existing 1.0.1
  installs cannot fake this: their table lacks the new columns. They must delete their `SMS`
  rows from `django_migrations`, `DROP TABLE SMS_smslog`, and re-run `migrate`, losing their
  sent-SMS log history. The owner accepted this cost explicitly. `UPGRADE.md` must document
  the exact procedure, prominently, as data-destroying.
- **D2 — Uniform HTTP response envelope.** Every API response, success or failure, has the
  shape `{"success": bool, "data": object|null, "error": object|null}`. On success `error` is
  null; on failure `data` is null and `error` is `{"code": str, "message": str, "detail":
  object|null}`. HTTP status codes remain meaningful (201 / 400 / 502 / 401 / 429) — the
  envelope is in addition to them, not a replacement. The Python library keeps returning the
  typed `SendResult` dataclass; the view converts at the boundary.
- **D3 — Django service-layer module naming.** `client.py` → `services.py`, `logs.py` →
  `repository.py`, `message.py` → `dto.py`. The `api/` subpackage stays. Class names are
  unchanged: `SmsClient`, `AsyncSmsClient`, `SmsLogRecorder`, `SmsMessage`, `SendResult`.
- **D4 — CodeQL removed.** `.github/workflows/codeql-analysis.yml` is deleted. `ci.yml` is the
  only workflow. Any task text saying to leave CodeQL untouched is void.
- **D5 — Documentation is Markdown and thorough.** `README.rst` is replaced by `README.md`
  (update `readme = "README.md"` in `pyproject.toml`). Task 15 produces genuinely complete
  docs, not a stub.
