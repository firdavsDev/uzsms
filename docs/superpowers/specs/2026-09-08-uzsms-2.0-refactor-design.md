# django-sms-uz 2.0 — Refactor Design

Date: 2026-09-08
Status: Approved (pending spec review)
Distribution name: `django-sms-uz` (unchanged)
Import package: `SMS` → `uzsms`
Django app label: `SMS` (unchanged, pinned)
Version: 1.0.1 → 2.0.0

---

## 1. Motivation

The 1.0.1 package is a single-file SMS sender with four correctness bugs, one
security hole, no tests, no timeouts, and build artifacts committed to git.
This refactor rebuilds it as a testable, pooled, backend-pluggable Django app
while preserving the existing database table and the old public callable names.

### Defects being fixed

Correctness:

- The DRF view passes a `requests.Response` object into `rest_framework.Response`,
  which cannot serialize it. The endpoint fails.
- The log row is written before the send and hardcoded to `is_active=True`, so the
  log claims success even when the broker rejects the message.
- `message-id` is the constant `"abc000000001"` for every message, exposing the
  caller to broker-side deduplication.
- The send method returns a `requests.Response` on success and a formatted string
  on failure, so callers cannot branch on the result.

Security:

- The send endpoint is `AllowAny`, making any deployment an open SMS relay and
  exposing the operator to toll fraud against their broker credits.
- The serializer places no `max_length` on `message`, allowing unbounded payloads.

Performance:

- No `timeout` is passed to `requests.post`, so a stalled broker pins a worker
  thread indefinitely.
- A new TCP and TLS handshake is performed per message; no session or pool reuse.
- The broker accepts an array of messages per call, but the code sends one message
  per HTTP request.
- Every send performs its own `INSERT`, producing N+1 write behavior for batches.

Design:

- Settings are read at import time, so importing the module without `SMS_SETTINGS`
  raises `KeyError`, and tests cannot override configuration.
- One class builds the payload, performs HTTP, and writes the database, leaving no
  seam for testing.
- Names (`SMS_Sender`, `SendSmsOneContact`) violate PEP 8.
- The serializer assigns to `self._errors`, a DRF internal.
- Dead imports and a duplicated import statement across `models.py` and `views.py`.
- `SmsLog` has no timestamps, no real status, no index, and no ordering.

Packaging and repository:

- `build/`, `dist/`, `*.egg-info`, and `__pycache__` are committed; there is no
  `.gitignore`.
- Legacy `setup.py` / `setup.cfg`; no `pyproject.toml`; dependencies undeclared;
  classifiers advertise Python 3.5.
- No test suite.

## 2. Decisions taken

| Question | Decision |
| --- | --- |
| Backward compatibility | 2.0 clean break, with deprecation shims for the old names |
| HTTP endpoint | Kept, authenticated by default, DRF moved to an optional extra |
| Performance scope | Pooling, timeouts, retry, bulk send, optional Celery task, plus an async client |
| Log model | Additive migration; `is_active` retained as deprecated |
| Package name | `uzsms`, with the Django app label pinned to `SMS` |
| Provider coupling | Swappable backend interface, Playmobile as the default |

### Why the app label stays `SMS`

Django records applied migrations in `django_migrations` keyed by app *label*,
not by module path, and derives the default table name from the label. Renaming
the Python package while pinning `label = "SMS"` in the `AppConfig` therefore
leaves both the `SMS_smslog` table and every applied-migration row untouched.
Existing deployments upgrade by editing `INSTALLED_APPS` and their imports; they
run no data migration and suffer no downtime. Migration files keep their existing
filenames (`0001_initial`, `0002_delete_smstoken`, `0003_remove_smslog_code`) so
Django continues to see them as applied.

## 3. Module layout

All modules live under the `uzsms/` package.

| Path | Responsibility |
| --- | --- |
| `__init__.py` | Public API re-exports and the deprecated aliases |
| `apps.py` | `UzSmsConfig`, with `name = "uzsms"` and `label = "SMS"` |
| `conf.py` | Lazy, validated access to `SMS_SETTINGS` |
| `validators.py` | `validate_uz_phone`, shared by client and serializer |
| `message.py` | `SmsMessage` and `SendResult` value objects |
| `exceptions.py` | Exception hierarchy |
| `backends/base.py` | `BaseSmsBackend`, `BaseAsyncSmsBackend` |
| `backends/playmobile.py` | Default backend, sync and async |
| `backends/console.py` | Writes messages to stdout |
| `backends/locmem.py` | Collects messages in memory for tests |
| `backends/dummy.py` | Discards messages |
| `backends/__init__.py` | `get_backend` loader with caching |
| `client.py` | `SmsClient`, `AsyncSmsClient` — orchestration only |
| `logs.py` | `SmsLogRecorder` — the sole writer of `SmsLog` |
| `models.py` | `SmsLog` |
| `admin.py` | `SmsLogAdmin` |
| `tasks.py` | Celery task, guarded by an import check |
| `api/serializers.py` | `SendSmsSerializer` |
| `api/views.py` | `SendSmsAPIView` |
| `api/urls.py` | URL patterns |
| `urls.py` | Thin re-export of `api.urls` with a dependency check |
| `compat.py` | `SMS_Sender` and friends |
| `migrations/` | Existing three migrations plus `0004` |

The old `SMS/` package directory is removed. Its modules move into `uzsms/` and
are decomposed as described above.

## 4. Configuration

Configuration continues to be read from a `SMS_SETTINGS` dictionary in the host
project's settings module, so existing deployments keep their settings block.

`conf.py` exposes a module-level lazy settings proxy. Values are resolved on first
attribute access, not at import time. A missing required key raises
`django.core.exceptions.ImproperlyConfigured` naming the key. The proxy subscribes
to Django's `setting_changed` signal and clears its cache, so
`override_settings` works in tests.

Required keys: `URL`, `LOGIN`, `PASSWORD`.

Optional keys and their defaults:

| Key | Default | Purpose |
| --- | --- | --- |
| `BACKEND` | `"uzsms.backends.playmobile.PlaymobileBackend"` | Dotted path to the backend class |
| `ORIGINATOR` | `"3700"` | Sender ID sent to the broker |
| `TIMEOUT` | `(5, 15)` | Connect and read timeout in seconds |
| `MAX_RETRIES` | `3` | Retry attempts on idempotent transport failures |
| `RETRY_BACKOFF` | `0.5` | Backoff factor between retries |
| `POOL_MAXSIZE` | `10` | Connection pool size |
| `LOG_MESSAGES` | `True` | Whether to write `SmsLog` rows |
| `FAIL_SILENTLY` | `False` | Return a failed result instead of raising |
| `MAX_MESSAGE_LENGTH` | `918` | Serializer and client validation ceiling |
| `PERMISSION_CLASSES` | `["rest_framework.permissions.IsAuthenticated"]` | Dotted paths for the view |
| `THROTTLE_RATE` | `"20/min"` | Rate for the send endpoint's throttle scope |

Retry policy applies only to connection errors and to broker responses in the
`5xx` and `429` range. A `4xx` response other than `429` is a permanent failure
and is not retried.

Retrying a send is not inherently safe, because a request that timed out may still
have been delivered. The retry is made safe by the stable per-message identifier:
`message_id` is generated once, before the first attempt, and reused across
retries, so the broker deduplicates a replayed message rather than sending it
twice. A backend that cannot offer this guarantee must set `MAX_RETRIES` to `0`
rather than risk duplicate delivery.

## 5. Value objects and exceptions

`SmsMessage` is a frozen dataclass carrying `phone_number`, `text`, and an
optional `message_id`. When `message_id` is absent the backend assigns
`uuid4().hex`, which resolves the duplicate-identifier defect.

`SendResult` is a frozen dataclass carrying `message`, `ok`, `provider_message_id`,
`status_code`, `raw`, and `error`. Every public send path returns `SendResult` or a
list of them. No public method returns a raw `requests.Response` or a string.

Exception hierarchy, all rooted at `SmsError`:

- `SmsConfigurationError` — missing or invalid settings, unloadable backend.
- `SmsValidationError` — phone number or message text rejected before send.
- `SmsTransportError` — network failure, timeout, retries exhausted.
- `SmsProviderError` — broker returned a non-success response; carries the status
  code and parsed body.

When `FAIL_SILENTLY` is enabled, the client catches `SmsTransportError` and
`SmsProviderError` and returns a `SendResult` with `ok=False` and `error` populated.
`SmsConfigurationError` and `SmsValidationError` always raise, because silently
swallowing them would hide programmer error.

## 6. Backend interface

`BaseSmsBackend` defines `open()`, `close()`, context-manager support, and
`send_messages(messages)` accepting a sequence of `SmsMessage` and returning a list
of `SendResult` in the same order. `BaseAsyncSmsBackend` mirrors it with
`async send_messages` and async context-manager support.

`get_backend(path=None)` imports and caches the configured class, raising
`SmsConfigurationError` on an unimportable path or a class that does not subclass
the base.

`PlaymobileBackend` holds a module-level `requests.Session` configured with an
`HTTPAdapter` carrying the pool size and a `urllib3` `Retry` policy built from the
retry settings. Every request passes the configured `timeout`. All messages in a
call are packed into the broker's native `messages` array, so sending N messages
costs one HTTP request rather than N. The response body is parsed once and split
back into per-message `SendResult` objects.

`AsyncPlaymobileBackend` implements the same contract over a shared
`httpx.AsyncClient` with equivalent timeout, pool, and retry configuration.

`ConsoleBackend` prints a readable rendering of each message and returns successful
results. `LocMemBackend` appends messages to a list attribute for assertion in
tests. `DummyBackend` discards messages and returns successful results. None of
these three perform network I/O, which is what allows the majority of the test
suite to run offline.

## 7. Client

`SmsClient` accepts an optional backend instance, defaulting to the configured one.
It exposes `send(phone_number, text)` returning a single `SendResult`, and
`send_bulk(messages)` returning a list.

The send flow is: validate every message, ask `SmsLogRecorder` to create pending
rows in one `bulk_create`, delegate to `backend.send_messages`, then ask the
recorder to apply outcomes in one `bulk_update`. A batch of N messages therefore
costs two queries and one HTTP request, replacing the current N inserts and N
requests. When `LOG_MESSAGES` is disabled the recorder is a no-op and no queries
are issued.

`AsyncSmsClient` offers the same two methods as coroutines over an async backend,
wrapping the recorder's ORM calls in `sync_to_async`.

`SmsLogRecorder` is the only module permitted to write `SmsLog`. Isolating it keeps
the client free of ORM concerns and lets tests substitute a recorder that records
nothing.

Phone validation lives in `validators.py` and is called by both the client and the
serializer. Today only the serializer validates, so direct library calls bypass the
check entirely; sharing one validator closes that gap and removes the duplication.
The rule requires exactly twelve digits matching the `998` country prefix.

## 8. Data model

Migration `0004` alters `SmsLog` additively:

| Field | Type | Notes |
| --- | --- | --- |
| `status` | `CharField` with choices `pending` / `sent` / `failed` | Indexed |
| `created_at` | `DateTimeField(auto_now_add=True)` | Indexed |
| `sent_at` | `DateTimeField(null=True)` | Set on a successful send |
| `message_id` | `CharField`, indexed | The identifier submitted to the broker |
| `provider_response` | `JSONField(null=True)` | Parsed broker body |
| `error` | `TextField(blank=True)` | Failure detail |

`text` widens from `CharField(max_length=255)` to `TextField`, which is a
non-destructive alteration. `Meta.ordering` becomes `("-created_at",)`. A composite
index on `(phone_number, created_at)` supports the common admin lookup.

`is_active` is retained so existing queries, admin filters, and integrations keep
working. It is documented as deprecated and is maintained as a mirror of
`status == "sent"`. It is scheduled for removal in 3.0.

The admin gains `status`, `created_at`, and `sent_at` in `list_display`, filters on
`status` and `created_at`, search on `phone_number` and `message_id`, and marks the
new provider fields read-only.

## 9. HTTP layer

The DRF integration moves into the `api/` subpackage and is imported lazily, so
installing the package without DRF is supported. `uzsms/urls.py` raises
`ImproperlyConfigured` with an actionable message if DRF is missing when the URLs
are included.

`SendSmsSerializer` declares `phone_number` validated by the shared validator and
`message` bounded by `MAX_MESSAGE_LENGTH`. It performs no assignment to DRF
internals; errors are raised through `ValidationError` in the normal way.

`SendSmsAPIView` resolves its permission classes from `PERMISSION_CLASSES`,
defaulting to `IsAuthenticated`, and applies a scoped throttle at `THROTTLE_RATE`.
This closes the open-relay hole. Deployments that genuinely want an unauthenticated
endpoint must opt in explicitly through settings.

The view returns a serializable JSON body containing the status, the provider
message identifier, and the log row identifier. HTTP `201` indicates the broker
accepted the message; a provider failure maps to `502`; a validation failure maps
to `400`. This replaces the current attempt to serialize a `requests.Response`.

---

## 10. Optional integrations

Extras are declared as `drf`, `async`, `celery`, and `dev`, installable as
`django-sms-uz[drf,async]`.

`tasks.py` attempts to import `shared_task` from Celery. If Celery is absent the
module defines a placeholder that raises a clear error when called, so importing
the package never fails. The task accepts a phone number and text, delegates to
`SmsClient`, and is configured with autoretry on `SmsTransportError`.

## 11. Backward compatibility

`compat.py` provides `SMS_Sender` with its original constructor signature, its
`SendSmsOneContact` method, and its `create_sms_log` method. Each emits a
`DeprecationWarning` naming the replacement and delegates to `SmsClient`. These
names are re-exported from `uzsms` so `from uzsms import SMS_Sender` works. They are
scheduled for removal in 3.0.

The `SMS_SETTINGS` settings key is unchanged, so no host project needs to rename
its configuration block.

One break is unavoidable and must be documented prominently: the top-level `SMS`
module no longer exists, so `from SMS.sms_utils import SMS_Sender` fails. The old
*names* survive; the old *import path* does not. Since the upgrade already requires
editing `INSTALLED_APPS`, this is a single coordinated edit rather than a separate
migration step.

`UPGRADE.md` documents the change as a short before-and-after table covering
`INSTALLED_APPS`, import paths, the new settings keys, and the return-type change
from `requests.Response` to `SendResult`.

## 12. Packaging and repository hygiene

`pyproject.toml` replaces `setup.py` and `setup.cfg`, using the setuptools backend
and PEP 621 metadata. The distribution name remains `django-sms-uz` so existing
`pip install` lines and the PyPI project are unaffected. `requires-python` becomes
`>=3.9`. Runtime dependencies are declared as `django>=4.2` and `requests>=2.28`;
the classifier list is corrected to the versions actually supported.

A `.gitignore` is added covering `build/`, `dist/`, `*.egg-info/`, `__pycache__/`,
`*.py[cod]`, `.pytest_cache/`, `.ruff_cache/`, virtualenvs, and editor directories.
The committed artifacts are untracked with `git rm -r --cached`. Git history is
**not** rewritten; that is a separate decision with coordination costs for anyone
holding a clone.

`ruff` is configured for linting and formatting.

`README.rst` is rewritten for the new import paths, the settings table, the backend
list, and both the sync and async usage. The stale "under repair" banner and the
broken image link are removed.

## 13. Testing

The project currently has no tests. The suite is written test-first, using pytest
with `pytest-django` against a minimal settings module.

Coverage targets:

- `conf.py`: missing required keys raise `ImproperlyConfigured`; defaults resolve;
  `override_settings` is observed.
- `validators.py`: accepted and rejected phone number forms.
- Each backend against its contract, with `LocMemBackend` asserting message capture.
- `PlaymobileBackend` against mocked HTTP (`responses`), asserting that a timeout is
  always passed, that N messages produce one request, that each message carries a
  distinct identifier, and that retry fires on `5xx` but not on `400`.
- `AsyncPlaymobileBackend` against `respx`.
- `SmsClient.send_bulk` under `assertNumQueries`, pinning the two-query behavior so
  the N+1 defect cannot silently return.
- Log rows: pending on creation, `sent` with `sent_at` on success, `failed` with
  `error` on failure, and `is_active` mirroring `status`.
- The view: an anonymous request is **denied**, an authenticated one succeeds, the
  response body is JSON-serializable, and throttling engages.
- `compat.py`: the old names work and each emits `DeprecationWarning`.

CI runs on GitHub Actions across Python 3.9 through 3.13 and Django 4.2 and 5.x,
running ruff and the test suite. The existing CodeQL workflow is retained.

## 14. Out of scope

- Rewriting git history to purge previously committed build artifacts.
- Additional providers beyond Playmobile. The backend interface makes adding one a
  single class, but none is written here.
- Delivery-report webhooks and inbound SMS.
- Renaming the PyPI distribution or the `SMS_SETTINGS` key.
- Removing `is_active`, which is deferred to 3.0.

---

## 15. Acceptance criteria

1. An existing 1.0.1 deployment upgrades by editing `INSTALLED_APPS` and imports,
   runs `migrate`, and applies only migration `0004`; the `SMS_smslog` table is not
   renamed and no rows are lost.
2. Importing `uzsms` with no `SMS_SETTINGS` defined does not raise.
3. Sending fifty messages issues one HTTP request and two database queries.
4. Every request carries a timeout and a unique broker message identifier.
5. An anonymous request to the send endpoint is rejected by default.
6. A successful send returns a JSON body; no code path returns a raw
   `requests.Response` or a bare string.
7. A failed send leaves a log row with `status="failed"` and a populated `error`.
8. The full suite passes offline against `LocMemBackend` and mocked HTTP.
9. `pip install django-sms-uz` succeeds without DRF, httpx, or Celery present.
